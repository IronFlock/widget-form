# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run start` — runs `vite build --watch` together with the Vite dev server on port 8000, auto-opening `/demo/`.
- `npm run build` — production library build via Vite (entry `src/widget-form.ts`, ES format, `dist/widget-form.js`).
- `npm run watch` — incremental library build only.
- `npm run types` — regenerates `src/definition-schema.d.ts` from `src/definition-schema.json` using `json-schema-to-typescript`. Run this whenever `definition-schema.json` changes.
- `just lint` — what the CI gate checks besides the build: regenerating the committed generated files (`npm run types`) changes nothing. `just build` = `npm run build`.
- `just merge` / `just release-patch` (`release-minor`, `release-major`) — pull requests into `main` from a feature branch with everything committed: a no-release one, or a release one whose merge publishes to npm in CI (`.github/workflows/build-publish.yml`), then the release GitHub App tags the bare version and creates the GitHub release. Never `npm publish`, tag or edit the version by hand.
- `npm run link` / `unlink` — link the local build into a sibling `../RESWARM/frontend` checkout for in-place testing.

There is no test suite or linter configured; Prettier config lives in `.prettierrc`.

## Architecture

This package ships a single Lit 3 web component, `widget-form`, consumed by the IronFlock/RESWARM dashboard platform. The whole component lives in `src/widget-form.ts`; everything else is configuration or generated.

### Versioned custom element tag

The class is registered as `widget-form-versionplaceholder`. The literal string `versionplaceholder` is rewritten to `pkg.version` at build time by `@rollup/plugin-replace` (configured in `vite.config.ts`). Consumers must therefore use a version-suffixed tag matching the installed package version, e.g. `<widget-form-1.0.16>`. This lets multiple versions of the widget coexist on the same dashboard page. When changing the version, no source edits are needed — the build substitutes it.

### Schema-driven configuration

`src/definition-schema.json` is the source of truth for the widget's configurable inputs. It is consumed two ways:

1. The IronFlock dashboard editor reads it (with custom keywords like `dataDrivenDisabled`, `condition.relativePath/showIfValueIn`, `targetColumn`, `order`, `required`) to render the widget's settings UI.
2. `npm run types` converts it into `src/definition-schema.d.ts`, which `widget-form.ts` imports as `FormConfiguration` / `FormFields`.

Always edit `definition-schema.json` first, then run `npm run types`. The descriptions in the schema are written for AI/LLM consumption (see commit `f2e58ea`).

### Component contract

- Inputs: `inputData: FormConfiguration` (form config + fields), `theme: { theme_name, theme_object }`, `route: string` (current dashboard route, used by `resolveRoute` for `*` segment substitution and `{{label}}` variable interpolation in `deleteNavigationRoute`).
- Outputs: dispatches `data-submit` (non-bubbling) with an array of `{ swarm_app_databackend_key, table_name, column_name, value }` mappings — one entry per `formField` plus an extra entry for `deleteFlagColumn` when present. On delete it additionally dispatches a bubbling/composed `nav-submit` event with the resolved route. A save with a new file dispatches `file-data-submit` instead (see File fields).
- Each field's `targetColumn` (type `targetColumn` in the schema) is the platform's database column picker; the host wires its value, and submission carries the same identifiers back so the host can persist data.
- Theming: reads `--re-text-color` and `--re-tile-background-color` CSS variables first, then falls back to `theme.theme_object`. Material Web tokens (`--md-sys-color-*`, `--md-menu-*`) are then re-derived from those values inside `render()`. These are not snapshotted: `registerTheme()` stores a `var(--re-…, <theme value>)` chain, so a change to the host property repaints the tile live without the widget being told. The dialog and select menus (`--md-dialog-container-color`, `--md-menu-*`, `--md-sys-color-surface-container`) need an opaque surface, and `--re-text-color` is picked to read on the tile as displayed, so `surfaceColor()` composites the tile colour over the dashboard's `--re-background-color` over white (the dashboard view's own colour). With no dashboard background (standalone, the demo) the theme background stands in for it. Studio 3.5.7 and earlier painted `--re-background-color` twice under the tiles (on `<main>` and again on `dashboard-navigator`), so there a translucent dashboard colour stacked up on screen and the surface came out slightly lighter than the tile; later studios paint it once, which is exactly what `surfaceColor()` models. It reads the variables in `render()`, because a `var()` chain cannot be composited in JS, and `opaqueSurface()` caches the `#rrggbb` result by the input strings. The browser parses each colour through a canvas `fillStyle`, and a value it rejects counts as transparent, as it does on the tile (rejection is detected by setting the value after two different placeholders, because a rejected value leaves the previous one in place). The blend itself is plain source-over in JS. Never read canvas pixels for it: under Firefox's `resistFingerprinting`, which Tor Browser turns on, `getImageData()` returns random colours. What floats above the tile is raised on a dark surface: `raisedSurface()` paints white at 16% (`RAISE_ON_DARK`) over a surface whose WCAG luminance is below 0.18 (`DARK_SURFACE`, about mid grey) and that colour fills `--md-dialog-container-color` and the `--md-menu-*` colours, while the scrim deepens from Material's 0.32 to 0.6 (`SCRIM_OPACITY_*`). A dark page barely changes under a 32% scrim, so a dialog in the tile's own colour sank into it (a popup form on a transparent tile over a dark dashboard is that colour exactly); Material 3 shows elevation in dark schemes by lightening a surface, and a shadow does not show on a dark page. Light surfaces keep the tile colour and the 0.32 scrim. `patchDialogScrim()` writes the opacity into the sheet it adopts into md-dialog's shadow root and rewrites it when the surface turns dark or light, because older browsers do not let `::backdrop` inherit custom properties.
- Form rendering uses Material Web (`@material/web` is a peer dependency, externalized in the rollup output). Inline mode renders fields directly; `formButton` mode renders a button that opens an `md-dialog`: a FAB unless `formButtonStyle.fab` is exactly `false` (unset keeps the FAB older tiles had; the schema's `default: true` makes the editor show it checked), else `renderOpenButton()`, an `md-filled-button` with the icon and `formButtonStyle.label`. An empty label stays empty on screen (no title fallback): the button then shows only the icon, centred by `ICON_ONLY_TRAILING_SPACE` (Material keeps its 8px icon gap with no label), and gets the FAB's `aria-label`, since `md-icon` is `aria-hidden`. Every `formButtonStyle` field but `fab` (the `label` condition's target, so it must stay literal) is bindable, so `openButtonStyle()` normalises the whole object before either button reads it: a label may be a finite number, a size outside the enum is medium, and a colour must pass `buttonColor()` (`CSS.supports('color')` with no `;`, `{`, `}` or `/*`, since a bound value is table data interpolated into a `style` attribute and `CSS.supports()` passes a trailing comment), else the default applies. Its icon is the Material icon named by `formButtonStyle.iconName` (a ligature in the Material Symbols font Studio loads, as in widget-sidenav), `add` when that is blank or not a string; the FAB's `aria-label` is the form title, else "Open form". The filled button takes the FAB's background; its label and icon default to black or white by contrast (`onColor()`) rather than the FAB's `theme.color[1]`, since text has to read, and `size` maps to 32/40/56px through `OPEN_BUTTON_SIZES` (medium is Material Web's own button, so it sets no tokens). `formButtonStyle.cornerRadius` (px) goes through `buttonRadius()` (a number of 0 or more, or a bound column's text that parses as one, rendered as `<n>px`, so nothing else reaches the `style` attribute; else '' and Material's own corners) and becomes `--md-filled-button-container-shape` on the regular button and `--md-fab-container-shape` on the FAB, set for all three FAB sizes (`FAB_SHAPE_SIZES`), since Material keeps a separate token per size (12/16/28px by default). The ripple and focus ring follow the same tokens, and CSS scales an oversized radius down to fully round. `formKey` is incremented to force a full re-render on reset. A dropdown's caption is the select's own floating label (`.label`, as on the text fields, so a select lines up with a text field beside it; before the layout change it was a caption above the box), never a `<label>` wrapping the select: the label would send the select a second click, which in Firefox closes the menu the first click opened. Reset and Cancel (`md-outlined-button`) take the text colour, because Material's fixed purple primary does not read on a dark surface. Both action rows wrap, so a narrow window cannot clip the leftmost buttons.
- Dialog size (`formButton` mode): `.form` gives the dialog `width: min(90vw, 480px); max-height: 80vh` on top of md-dialog's `:host` `min-width: 280px; min-height: 140px; max-width`/`max-height: min(560px, calc(100% - 48px))`, which the native `<dialog>` inherits through the `display: contents` host. `formDialogSize.minWidth`/`minHeight` go through `dialogMinSize()` and land in md-dialog's `style` attribute as `min-*: min(<value>, calc(100% - 48px))`. That replaces md-dialog's 280x140px floor outright (a smaller value, 0 included, lowers it, and below a 328px-wide window any value lets the dialog shrink to the cap) and beats `.form` and md-dialog's `max-*` whenever it is larger; with neither set there is no `style` attribute. `%` is a share of the window because `showModal()` puts the dialog in the top layer. Keep the cap: the dialog swallows Escape and backdrop clicks, so its action bar is the only way out, and an uncapped minimum pushes it off the screen. Keep the grammar strict too (`DIALOG_MIN_SIZE`: a number plus an optional px, %, vw, vh, rem or em; no unit means px; empty or unset keeps the default, while 0 is a real minimum like any other value; anything else warns once and is ignored). `CSS.supports()` is no substitute: it accepts `800px/*`, whose comment swallows the cap and every declaration after it. The schema `pattern` on both leaves spells the same grammar (lowercase units only, and an explicit ASCII whitespace class, because the AI checks it with Python's `re`, whose `\s` also matches U+001C-U+001F and U+0085) so the AI's `validate_widget` rejects what the widget would ignore; change them together.
- Validation Message (`validationMessage`, text and secret fields): md-outlined-text-field has no setting for a pattern-mismatch message (a `validation-message` attribute, which the widget used to set, does nothing), so the browser's generic "Please match the requested format" showed. `syncValidationMessage()` runs on the field's `input` and makes the message its custom validity while `validity.patternMismatch` holds, clearing it otherwise; md shows it as the error once the form reports validity. A pre-filled text value that was never edited still gets the browser's message. For a secret field, `validation` is its minimum-requirements regex; no separate key, so the editor and the AI see one regex for both types.
- Hidden fields (`hiddenField: true`) are not rendered; `currentRawValue()` submits their pre-filled or default value. Checkbox values are normalized to `'true'`/`'false'` then to booleans in `formatValue`.
- Highlight colour: `render()` sets Material's `--md-sys-color-primary` (the focused field's outline and label, checked checkboxes, the Submit button) and `--md-focus-ring-color` from `accentColors()`, in place of Material's fixed purple, which did not read on every tile. `accentColor` from the config is taken as written; unset, the theme's first palette colour is used when it has at least 3:1 WCAG contrast (`ACCENT_CONTRAST`) against the surface the fields sit on (the raised dialog in `formButton` mode, else the tile); otherwise the text colour. `--md-sys-color-on-primary` is black or white, whichever contrasts more, and the surface itself on the text colour.
- Error colour: `render()` sets `--md-sys-color-error` from the surface, Material's light-scheme `#b3261e` or, on a dark surface (`isDarkSurface()`), its dark-scheme `#f2b8b5`; the light red does not read on a dark tile or dialog. It covers the text fields' own error states too.

### Layout

The form (`.form-content`, the `<form>` itself) is a 12-column CSS grid that the fields fill left to right in array order; a field that does not fit on the current row starts the next one. Every field's root element (all nine render functions return exactly one) carries `w-<width>` (`fieldWidths()`, one pass over the list: the field's `width`, else the `groupWidth` of the section it is in, else `fieldLayout.defaultWidth`, else `full`; anything not in `FIELD_WIDTHS` counts as unset) and `new-row` for `newRow: true`. The span classes use the longhand `grid-column-end: span N`, so `.new-row`'s `grid-column-start: 1` survives. Unset, every field spans 12, which is the old single column; the unconfigured demo (`?layout=none`) matches 1.0.47 except for the dropdown, which is 24px shorter now that its label is inside the outline.

- **`align-items: start`** on the grid is required: `md-outlined-text-field` fills whatever height it gets, so a stretched field beside a textarea drew a textarea-tall outline.
- **Collapse by container queries.** The form has `container-type: inline-size`, and `collapseRules()` writes three `@container` blocks into the dynamic `<style>` in `render()`, because their thresholds come from `fieldLayout.minFieldWidth` (`fieldLayoutSettings()`: a number of 0 or more, numeric text too; else `DEFAULT_MIN_FIELD_WIDTH`, 180; 0 writes no rules) and the density's column gap. A span-n field is n/12 of the row less its share of the gaps (`FIELD_GAP` 16, `COMPACT_FIELD_GAP` 12; keep them equal to the two `column-gap`s), so quarters reach the minimum m at 4m + 3 gaps, thirds at 3m + 2, halves at 2m + 1. The ladder moves partners together so a pair stays on one row: below 4m + 3g quarters span 4 and three-quarters 8; below 3m + 2g every fraction spans 6; below 2m + g everything spans 12. The rules have the same specificity as each other and more than the base classes, so the later, narrower block wins without `!important`. No ResizeObserver, nothing to re-attach on reconnect; a closed dialog or a hidden page (0 wide) matches every rule, which is harmless.
- **Why 180.** The default 480px dialog gives its fields 432px, or 415 to 417 with a classic scrollbar (15 to 17px). At 200 two halves need 416, so a long form on Windows fell to one column while a short one kept two. Chromium shows a full date and time at 160px; Material's 210px select minimum is overridden (`md-outlined-select { min-width: 0 }`).
- **Fixed-width types.** Number, date and colour fields used an inline `style="width: 200px"`. Now they carry `fixed-width`, and `.fixed-width.w-full` is `width: 200px; max-width: 100%`, so on a full row they look as before (and shrink in a tile under about 232px instead of overflowing), while on part of a row they fill their cell. One that collapses to a full row has no `w-full` and fills it.
- **Checkboxes** on part of a row (`.checkbox-container:not(.w-full)`) get `min-height: 56px`, so they sit centred beside a text field's box. On a full row they keep their old height.
- **Density.** `fieldLayout.density: 'compact'` sets the host attribute `compact` in `updated()`, next to `fab-mode`, and the static `:host([compact])` rules do the rest: Material's size tokens (text fields have their own; a select's inner field reads `--md-outlined-field-*` directly, so both sets are needed), 32px buttons, icon buttons and checkbox halos, 14px text, smaller gaps and section spacing. Keep them static: Lit adopts the static styles as constructed sheets, which come after a `<style>` element in the cascade, so the same rule in `render()`'s `<style>` would lose at equal specificity. Anything other than `'compact'`, unset included, is comfortable, Material's size, so every existing form keeps its look; new forms start compact through `default-data.json` (below), and the schema description tells the AI to set it, since the AI stores its configs verbatim and never merges the default config.
- **File fields** keep their caption above the drop zone, so beside a text field their box sits lower. Documented in the README rather than solved: a notched outline over a translucent tile needs Material's border splitting.

**Sections** are `type: 'section'` entries in the same flat `formFields` list, not nested groups, so index keys (`column-${i}`, the per-field `@state` records, the `repeat` key), label references and the editor's tabs all keep working. `renderSection()` draws an `h4` and a `.section-hint` (not `h3`/`p`, which the shadow root styles for the form's title and subtitle) across the row, with a top border except as the form's first element (`:first-child` counts elements only, so hidden entries before it do not matter). A section groups the entries after it up to the next one (`sectionOf()`); sections do not nest.

- `isFieldVisible(field, i)` checks the field's own condition (`passesCondition()`, the old body) and, for a non-section, its section's. Its three callers are `renderForm()`, `handleFormSubmit()` and `withoutHidden()`, so a hidden group's fields submit null (with their file companions) and lose a chosen file or a typed colour, exactly as a condition-hidden field does. `hiddenField` members keep submitting, because `handleFormSubmit()` exempts hidden fields from conditions, as before.
- A section is never a value: `handleFormSubmit()` skips it before building its target (no item at all), `refreshFieldValues()` skips it (a later section with a field's label would otherwise overwrite that field's value with `''` and break every condition on it), and `passesCondition()`'s controller lookup skips it.
- A section with `hiddenField` hides its heading but still groups. A section ignores `width`, `newRow` and `required` (its width is always the full row); the schema hides those, `hiddenField` and `targetColumn` on a section's tab, and shows `groupWidth` only there.
- `renderForm()`, `handleFormSubmit()` and `refreshFieldValues()` skip `null` entries (a stray `-` in a board template).

**The schema budget.** The AI gets the full schema only while `json.dumps({package_name, version, definition_schema, default_config}, indent=2)` stays under its `MAX_WIDGET_SCHEMA_CHARS`, 50,000 since the ai service's change of 2026-10-29 (40,000 before; `check_widget.py` warns at the same number). The layout features took widget-form from 35,810 to about 43,000, so **a release with them needs that ai service deployed first**, or the AI gets only an overview of the form. The JSON is indented, so depth costs: each `condition` on `../type` inside a field costs about 430 characters, each six-item enum with `enumLabels` about 400. The input-type conditions list `false` so a new field tab with no type yet still shows its settings (the editor, the AI and the board checker all read an unset target as `false`, and `check_widget.py` accepts it since the same day).

`default-data.json` shows half-width fields and one section with a `groupWidth`, and sets `fieldLayout.density: 'compact'`, so a form dropped on a board starts compact (Studio's `defaultToTemplate()` stores it as `$str:compact`). Nothing else of `fieldLayout` goes there: Studio's editor writes a default-config value into every field that was never set when it shows that field (array items no longer, since Studio's 2026-10-15 fix in `schema-array.ts`), so a default width there would change existing forms on their next edit. For density that is accepted: the editor reads the default config of the tile's pinned version, so only a tile moved to this version or later is affected, and only once someone expands its Field Layout group (a collapsed group renders no fields) and saves; the preview shows it first.

### File fields

A `file` field uploads one file into a FleetFiles namespace of the target table's app and writes the stored object's key into `targetColumn`. The widget never uploads: Studio does (widget-item `handleFileDataSubmit`, module `fleetfiles-upload.ts`).

- **Its own event.** A save that carries a new file dispatches `file-data-submit`, never `data-submit`: an older Studio would serialize the `File` as `{}` into the column. The detail is `{ items, waitUntil }`; items are data-submit items plus file items `{ swarm_app_databackend_key, table_name, column_name, file, namespace, contentType, urlColumn? }`, where `urlColumn` is the field's `fileUrlColumn` as a target ref: the host writes the stored object's permanent URL there (the SDK's `files.url()` string, built from the file catalog's `public_base_url` and `sad_key`), null when it cannot build one. The host claims the event by calling `waitUntil(promise)` during the dispatch; unclaimed (an older Studio, which ignores unknown events) means no host can upload, and the form says so and saves nothing (`submitWithFiles`). While the promise is pending the actions are disabled and Submit reads "Saving…"; a resolve resets the form and closes the dialog, a reject keeps everything and shows `error.message` in `.form-error` (Studio's messages are localized and say whether anything was saved). Keep `FileDataSubmitDetail` and Studio's `handleFileDataSubmit` in step.
- **The dialog stays open** for it: md-dialog closes on every `method="dialog"` submit that bubbles to it, whatever `preventDefault()` says, so `handleFormSubmit` stops propagation on the file path. The plain `data-submit` path still closes at once, as before.
- **Keep, never null.** `fileFieldItems()`: a new file → the file item plus the name, size and type companion columns (`fileNameColumn`, `fileSizeColumn`, `fileTypeColumn`); no new file → the pre-filled key written back, or, with none, the column left out (fleetdb carries an absent column over on entity tables and leaves it NULL otherwise; an explicit null would clear it). Companions are only written with a new file. Delete never uploads. A field hidden by Conditional Display submits null with its companions and its URL column, like every other field.
- **The URL column** (`fileUrlColumn`) only the host can fill. With a new file the widget sends a null item for it *ahead of* the file item, which carries it as `urlColumn`. Studio's `writeRows` lets a later item for a column win, so its URL replaces the null, while an older host, which ignores `urlColumn`, still clears the column instead of carrying the previous file's URL over on an entity table. Keep that order.
- **The control** is a drop zone with a transparent native `<input type="file">` stretched over it (`.file-input`): the input takes clicks, keyboard focus and drops itself, and its `required` and the browser's message are anchored on the box. It has no `name`, so FormData never carries the file; the chosen `File` lives in `chosenFiles` (by field index), which survives the frequent new `inputData` objects, is cleared by reset, and is pruned in `willUpdate()` when a condition hides the field (its input is gone). A refused file is cleared from the input, or it would satisfy `required`. The clear button is an `md-icon-button type="button"` above the input (`z-index`); its default `type` is submit. Over a disabled input, the box swallows drops, or the browser would open the file in place of the board.
- **Types.** `acceptedFileTypes` entries are MIME types (`type/*` allowed), lowercased; other entries are dropped with a warning. FleetFiles matches content types case-sensitively, without parameters, with only a trailing `/*` as a wildcard, and turns an empty type into `application/octet-stream`, so `fileContentType()` sends the browser's type (lowercased, parameters cut) when it is accepted, else the type the extension stands for (`EXTENSION_TYPES`): Windows with Excel calls a CSV `application/vnd.ms-excel`, and unknown extensions come as `''`. The `accept` attribute lists the matching extensions too, so the system picker offers those files. The schema `pattern` spells the same grammar for the AI.
- **Sizes.** `maxFileSizeMB` counts 1,048,576 bytes per MB, like `formatBytes()`. FleetFiles takes up to 6 MiB in one call; above that Studio needs a presigned URL, which appliances cannot issue, and the namespace's `maxObjectBytes` applies everywhere. Studio checks both and says which limit a file broke.
- **The key** is Studio's choice: `<YYYY-MM-DD>/<random>/<file name>`, whose last segment is the sanitized original name (apps such as LineOps read the name and extension from it, and the form shows it for a pre-filled key).
- `default-data.json` has no file field and must not get one, nor any `targetColumn`: a namespace and a target column only exist in a running project. The demo adds file fields itself, and has `?oldhost` (no handler for `file-data-submit`), `?dialog`, `?label=<text>` (the regular open button), `?size=` and `?theme=chalk|vintage` switches; its stand-in host refuses files whose name contains "fail".

### Secret fields

A `secret` field (`renderSecretField`) is an `md-outlined-text-field` with an eye `md-icon-button` in its `trailing-icon` slot (`type="button"`, since its default is submit) that shows the value; `revealedSecrets` holds that per field index and reset clears it. What it is depends on `browserPasswordManager`. Off (unset, the default): a `text` input with `autocomplete="off"`, drawn as discs by `-webkit-text-security` (Chrome, Safari, Firefox 114+) while the host has the `masked` attribute. Browsers and extensions offer to save every `password` input whatever `autocomplete` says, which is what made a PIN annoying, so only a text input escapes them. The mask has to sit on the inner `<input>` in the text field's shadow root (on the host it would mask the label and hint too, as the property applies to any text), so `patchSecretFields()` adopts `secretMaskSheet()` there and, once the text field has rendered, sets `UNMANAGED_INPUT_ATTRIBUTES` on the input (no autocapitalize, autocorrect or spellcheck, which a phone would apply to a value nobody can see, plus the 1Password, LastPass, Bitwarden and Dashlane opt-outs), removing them again if the setting is switched on. `copy` and `cut` (composed events) are cancelled on the host while masked, as a password input does. On: a `password` input with `autocomplete="new-password"`, so the browser may offer to generate and save one but does not fill in the viewer's saved Studio login; revealing switches it to `text`. It is write-only: a saved secret is never read back, so it ignores `preFilledValue` (the schema hides it for secrets) and always starts empty. An empty input leaves the column out of the save (`secretFieldItems()`), which carries the stored secret over on an entity table (`maintainLatestFlagFor`) and stores NULL elsewhere. Do not send fleetdb's keep sentinel (`__secret__` or Studio's `••••••••`) instead: fleetdb resolves it by the same carry-over, but on a table without an entity key it throws `secret_sentinel_unresolvable` for the whole row, which Studio's pub/sub write never sees (the form would report success), and the widget cannot tell whether its column is `secret: true`, so a plain column would store the sentinel literally. Encryption is fleetdb's job (`secret: true` columns); the widget only masks. The typed value is sent untrimmed. Like file fields, it stays out of `default-data.json`; the demo adds two.

### Colour fields

A `color` field (`renderColorField`) is an `md-outlined-text-field` (200px on a full row, like number and date fields; see Layout) holding the colour as text, with a `.color-swatch` in its `trailing-icon` slot and a transparent native `<input type="color">` stretched over the swatch (as over the file drop zone), which opens the browser's picker on a click, Enter or Space. The text field holds the value, because a native colour input can never be empty (so neither `required` nor "use the default" would work) and knows only `#rrggbb`. The native input has no `name`, so FormData carries only the text.

- **Stored as hex.** `colorHex()` turns any CSS colour into lowercase `#rrggbb`, or `#rrggbbaa` below full opacity, so every consumer can read the column (zrender parses no `oklch()`, for instance); hex digits without the `#` count. It needs both `CSS.supports('color')` and `readColor()` (the canvas parse `parseColor()` is built on, which says when the browser rejects a value): the first refuses what only the `color-mix()` fallback would turn into a colour, the second the CSS-wide keywords that `CSS.supports()` passes; `currentColor` is refused too, since it names no colour of its own. `formatValue()` stores the hex, null for an empty field without a default, and a text that is no colour as it was: typing one sets `COLOR_MESSAGE` as the custom validity and blocks the save, so only an untouched pre-filled value gets there, and that is written back unchanged.
- **What is shown is what is stored.** Pre-filled and default values are displayed as their hex (the default as the placeholder), and a typed colour is rewritten as hex on `change`. Setting md's `value` updates its form value synchronously, so the form's `@input`/`@change` handler, which the same events reach afterwards, reads the new value for Conditional Display.
- **Events from the picker bubble through the text field.** The native input is a light-DOM child of the text field, so its `input` and `change` reach the text field's listeners too; `colorTextField()` keeps those to events whose target is the text field itself.
- **The swatch** shows the typed colour, else the default (what a save stores then), over a checkerboard; with neither, or with text that is no colour, a diagonal stroke (`[empty]`). `typedColors` holds the text since it was edited, with the pre-filled value it was typed over: a new pre-filled value resets the text field through its `.value` binding, and the swatch then follows that again. `willUpdate()` prunes it for fields a condition hides, like `chosenFiles`, and reset clears it. Picking keeps the alpha of a translucent colour typed before, as the native picker has none.
- **Keys.** `preFilledValueColor` and `defaultValueColor` are `type: "color"` twins of `preFilledValue`/`defaultValue`, so the editor shows its colour picker (it stores hex, `''` when cleared); a blank one falls back to the plain key, which the AI may write. Like file and secret fields, colour fields stay out of `default-data.json`; the demo adds two.

### Build pipeline notes

- `vite.config.ts` externalizes `@material/web/*` and `lit-flatpickr` so consumers provide them. `tslib` is aliased to its ES module entry.
- `vite-plugin-dts` emits one declaration per source file (`dist/widget-form.d.ts`, plus `dist/definition-schema.d.ts` copied from `src`). It does not roll them up: bundling needs `@microsoft/api-extractor`, whose `argparse` -> `sprintf-js` chain has no patched release.
- The demo (`demo/index.html`) imports `../src/widget-form.js` directly and computes the tag from `package.json` version, mirroring how the platform consumes the published build.

## `aiSelection` in `src/definition-schema.json`

The schema root carries an `aiSelection` block next to `title` and `description`. It is **not** JSON Schema and describes no config field — it exists so the IronFlock AI's Widget Builder can pick the right widget for a given shape of data, using knowledge only the widget author has:

```jsonc
"aiSelection": {
  "dataShape": "…what columns this widget consumes and what each one means…",
  "useWhen":   ["…a situation, naming the properties that express it…"],
  "notFor":    ["…a situation this widget is wrong for, naming the widget to use instead…"]
}
```

It is inert everywhere else, and must stay that way: `json2ts` ignores it (the generated `.d.ts` is byte-identical with and without it), the dashboard config editor renders only `schema.properties`, and the AI service's `validate_widget` validates *configs* against the schema, skipping unknown Draft-7 keywords.

When maintaining it:

- `notFor` is the high-value half and the part plain descriptions always omit. Every entry must name the widget that *should* be used, or it rejects without routing.
- Write for an LLM with no other documentation: describe the visible result and the user's intent, not the implementation.
- Prefer entries that discriminate against a *neighbouring* widget. Generic rejections are cheap; the ones that pay are those an author could plausibly get wrong.
- The `notFor` lists are a set across all `widget-*` repos and are meant to be reciprocal — if this widget routes to another for some case, that widget should usually route back for the converse. Changing one side is a cue to check the other.
- Update it whenever a property changes what this widget can *do*, not just how it looks.
